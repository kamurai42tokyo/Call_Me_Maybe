CHAPTER I

はじめに

古代ローマの技術者は、帝国中の穀物輸送を記録するために完璧な格子を刻んだ石板を使い、悪筆のせいで荷が失われないようにした。1800年代の船乗りは海流を構造化された表に記録し、その精度はいまでも航海に使われるものがあるほどだった。

最初の天気予報は、決まった符号の電報で送られた — 数個の数字で空全体を表せたのだ。1960年代の NASA 管制室では、誰が当番でも点滅するランプの意味が正確に分かるよう、ラミネート加工されたフローチャートを使っていた。スーパーのバーコードスキャナーは、多くの家庭にコンピュータが来るずっと前から白黒の縞を在庫データに変換していた。養蜂家でさえ何十年も標準化された用紙を使い、巣の健康状態や蜜の流れ、女王蜂の系統を、本人だけがひと目で読める小さな枠に記録してきた。

人類は常に、情報を信頼でき、共有でき、使えるものにするための構造を作ってきた。そして今日、目指すのは AI にコンピュータの言葉を話させること だ。

学習の過程で、AI はさまざまな作業を手助けしてくれる。AI ツールの能力や活用法を探る時間をとろう。ただし、常に慎重に向き合い、結果を批判的に評価すること。コードでも、ドキュメントでも、アイデアでも、技術的な説明でも、質問がうまく組み立てられていたか、生成内容が正確かを完全に確信することはできない。仲間（ピア）は、ミスや見落としを防ぐための貴重な存在だ。

  • 将来のキャリアに役立つプロンプト力（コーディング・非コーディング両方）を伸ばそう。
  • AI の仕組みを学び、よくあるリスク・バイアス・倫理的問題を予測して避けられるようにしよう。
  • 仲間と協力しながら、技術力とヒューマンスキルの両方を伸ばし続けよう。
  • 自分が完全に理解し、責任を持てる AI 生成コンテンツだけを使おう。

学習者のルール

  • プロンプトを書く前に問題をよく考えること。より明確で詳細、的確な語彙のプロンプトが書けるようになる。
  • AI が生成したものは、体系的にチェック・レビュー・疑問視・テストする習慣をつけること。
  • 常にピアレビューを求めること。自分だけの確認に頼らないこと。

このフェーズで得られる成果

  • 汎用的なプロンプト力と、分野特化のプロンプト力の両方を伸ばす。
  • AI ツールを効果的に使い、生産性を上げる。
  • 計算論的思考・問題解決力・適応力・協調性を引き続き強化する。

コメントと例

  • 試験や評価など、本当の理解を示さなければならない場面は何度もある。準備を怠らず、技術力と対人スキルを磨き続けよう。
  • 自分の考えを説明したり仲間と議論したりすると、理解の穴が見つかることが多い。ピアラーニングを優先しよう。
  • AI ツールはあなた固有の状況を知らず、一般的な回答をしがちだ。同じ環境にいる仲間の方が、的確な助言をくれることがある。

✓ 良い例

✗ 悪い例
AI に関数まるごと書かせてコピペする。ピア評価で、それが何をするのか・なぜそうなのか説明できない。信用を失い、課題も落ちる。
✓ 良い例

プロジェクトの重要部分を Copilot に生成させる。コンパイルは通るが、パイプの扱いを説明できない。評価で根拠を示せず、課題を落とす。
CHAPTER III

イントロダクション

III.1 Function Calling（関数呼び出し）とは？

大規模言語モデル（LLM ＝ChatGPT のような文章を作る AI）は人間の言葉を理解・生成するのは得意だが、構造化された、機械がそのまま実行できる出力を自然には作れない。Function Calling は、自然言語のリクエストを型付きの引数を持つ正確な関数呼び出しに翻訳することで、このギャップを埋める。

例：自然言語 → 関数呼び出し

User: "What is the sum of 40 and 2?"

Traditional LLM: "The sum of 40 and 2 is 42."

Function Calling System:
{
  "function": "add_numbers",
  "arguments": {"a": 40, "b": 2}
}

Function Calling システムは質問に直接答えるのではない。代わりに、それを解くための道具 — 正しい関数名と、正しい型の引数 — を提供するのだ。

III.2 なぜ重要なのか？

Function Calling によって LLM は次のことができるようになる：

  • 外部システムとの連携：API を呼ぶ、データベースに問い合わせる、デバイスを制御する
  • コードの実行：計算、データ変換、ファイル操作
  • 操作の連鎖：複雑なタスクを実行可能なステップに分解する
  • 構造化された出力：JSON や XML など機械が読める形式を生成する
  • 非構造テキストからの構造化データ抽出：例えば長い本から {主人公の名前, 主人公の性別, 主人公の年齢} のような項目を抜き出す

この技術は現代の AI アシスタント、コード生成ツール、自律エージェントを支えており、生テキストからの自動情報抽出や知識の構造化も可能にしている。

III.3 課題

小さな言語モデル（今回使う 0.6B ＝6億パラメータ のモデルなど）は、構造化された出力を生成するのが苦手なことで知られている。JSON を出せと指示しても、成功するのは 30% 程度かもしれない。それでも実運用のシステムは、同じ小さなモデルで 99% 以上の信頼性を達成している。

どうやって？ その答えが Constrained Decoding（制約付きデコーディング） だ。プロンプトだけに頼らず、モデルの出力をトークン （＝単語のかけら） 単位で誘導し、正しい構造を保証する技術である。

CHAPTER IV

共通の指示

IV.1 一般ルール

  • プロジェクトは Python 3.10 以上で書くこと。
  • flake8 のコーディング規約に従うこと。
  • 関数は例外を適切に処理し、クラッシュを避けること。try-except で起こりうるエラーを扱い、ファイルや接続などのリソースにはコンテキストマネージャ （＝with 文） を使って自動で後片付けされるようにすること。レビュー中に未処理の例外でクラッシュした場合、動作しないものとみなされる。
  • すべてのリソース（ファイルハンドル、ネットワーク接続など）はリークしないよう適切に管理すること。可能な限りコンテキストマネージャを使うこと。
  • 関数の引数・戻り値・変数（必要な場合）に型ヒントをつけること（typing モジュールを使用）。静的型チェックには mypy を使い、すべての関数が mypy をエラーなしで通ること。
  • 関数とクラスには PEP 257 に従った docstring（Google スタイルや NumPy スタイルなど）を書き、目的・引数・戻り値を記述すること。

IV.2 Makefile

よく使う作業を自動化する Makefile を用意すること。以下のルールを含めること（lint は指定のフラグ必須。より厳しいチェックとして --strict を試すことを強く推奨）：

  • 動作確認用のテストプログラムを作ること（提出・採点対象外）。pytest や unittest を使い、エッジケースもカバーすること。
  • Python の生成物を除外する .gitignore を含めること。

プロジェクト固有の追加要件がある場合は、このすぐ下に記載される。

IV.3.1 追加要件

  • すべてのクラスはバリデーション（値のチェック）に pydantic を使うこと。
  • numpy と json パッケージは使用可。
  • dspy（およびそれに類するパッケージ）の使用は完全禁止。pytorch、huggingface 系パッケージ、transformers、outlines なども含む。

    • Qwen/Qwen3-0.6B（デフォルト）

CHAPTER V

必須パート

V.1 概要

このプロジェクトでは、自然言語のプロンプトを構造化された関数呼び出しに変換するツールを作る。「What is the sum of 40 and 2?」という質問に対して、42 を返すのではなく、次を出力する：

  • 関数名：fn_add_numbers
  • 引数：{"a": 40, "b": 2}

実装では Constrained Decoding を使い、100% 有効な JSON を保証すること。それにより 0.6B パラメータの小さなモデルでも、ほぼ完璧な信頼性を実現する。

V.2 入力ファイル

data/input/ にある 2 つの入力ファイルを処理する：

function_calling_tests.json

システムが処理すべき自然言語プロンプトの JSON 配列。

[
  { "prompt": "What is the sum of 2 and 3?" },
  { "prompt": "What is the sum of 265 and 345?" },
  { "prompt": "Greet shrek" },
  { "prompt": "Greet john" },
  { "prompt": "Reverse the string 'hello'" },
  ...
]

functions_definition.json

システムが呼び出せる関数の一覧。各関数は次を含む：関数名／引数の名前と型／戻り値の型／説明

[
  {
    "name": "fn_add_numbers",
    "description": "Add two numbers together and return their sum.",
    "parameters": {
      "a": { "type": "number" },
      "b": { "type": "number" }
    },
    "returns": { "type": "number" }
  },
  {
    "name": "fn_greet",
    "description": "Generate a greeting message for a person by name.",
    "parameters": {
      "name": { "type": "string" }
    },
    "returns": { "type": "string" }
  },
  {
    "name": "fn_reverse_string",
    "description": "Reverse a string and return the reversed result.",
    "parameters": {
      "s": { "type": "string" }
    },
    "returns": { "type": "string" }
  },
  ...
]
⚠ 注意これらの例は想定される難易度の目安である。実際には別のプロンプトや関数セットでテストされる。入力ファイルが不正な JSON だったり存在しなかったりする可能性があるので、適切な JSON エラー処理を実装すること。

V.3 LLM とのやりとり

V.3.1 LLM SDK

このプロジェクトには、LLM を操作するためのラッパークラス Small_LLM_Model が llm_sdk パッケージ内に付属している。主なメソッドは以下：

メソッド説明
get_logits_from_input_ids(input_ids: List[int]) -> List[float]トークン ID のリストを受け取り、LLM が出力したロジット （＝次の各トークンの「ありえそう度」スコア） を返す。
get_path_to_vocab_file() -> strトークン ID とトークンの対応表（語彙ファイル）のパスを返す。
encode(text: str) -> Tensorモデルのトークナイザで文字列をトークン ID のテンソル （＝数値の配列） に変換する。
decode(token_ids: List[int]) -> str（任意）トークン ID のリストを文字列に戻す。

V.3.2 生成パイプライン

LLM の生成は次の手順で進む：

  1. プロンプト：自然言語の質問。例："What is the sum of 2 and 3?"
  2. トークン化：テキストをサブワード単位（トークン）に分割する。単純な単語分割と違い、トークナイザは先頭の空白を含めたり、句読点を扱ったり、BPE や SentencePiece などのアルゴリズムで単語をさらに細かく分けたりする。
    例（実際に近いもの）：["What", "Ġis", "Ġthe", "Ġsum", "Ġof", "Ġ2", "Ġand", "Ġ3", "?"]
    ※ 記号 Ġ は直前に空白があることを表す。実際のトークナイザは、テキストを正確に復元するためにこうした細部を保持している。
  3. 入力 ID：トークンをモデルが理解できる数値 ID に変換する。例（説明用）：[892, 318, 262, 4771, 286, 16, 290, 17, 30]
  4. LLM 処理：モデルがニューラルネットワークでこれらの数値を処理する。
  5. ロジット：モデルが、次に来うる各トークンの確率スコアを出力する。例：token_5: 0.001, token_42: 0.85, token_100: 0.02, ...
  6. トークン選択：確率をもとに次のトークンを選ぶ（通常は最もスコアの高いもの）。
    この段階で Constrained Decoding のような技術を適用し、選べるトークンを制限して、100% 有効な JSON のような特定の構造に従わせることができる。

重要：この処理はトークン 1 つずつ繰り返される。生成されたトークンはプロンプトに追加され、応答が完成するまで手順 2〜6 を繰り返す。

簡略図：

Prompt→ Tokenization→ Input IDs→ LLM→ Logits→ Next Token Selection

V.3.3 Constrained Decoding を理解する

言語モデルはテキストを 1 トークンずつ生成する。各ステップで、モデルは次に来うる全トークンの確率分布（ロジット）を出す。通常は、この分布からサンプリングするか、最も確率の高いトークンを選ぶ。

Constrained Decoding は、トークンを選ぶ前にロジットを書き換えることでこの過程に介入する：

  1. モデルが全トークンのロジットを出す。
  2. 有効な JSON 構造かつ想定スキーマ （＝データの形のルール） に適合するトークンがどれかを判定する。
  3. 無効なトークン（スキーマや構造を壊すもの）のロジットを負の無限大にする。
  4. 残った有効なトークンの中からだけ選ぶ。

このプロジェクトでは、Constrained Decoding は構文的に正しい JSON を保証するだけでなく、特定のスキーマも強制しなければならない。例えば functions_definition.json でフィールドが number と定められていれば、デコーダは整数または小数を満たす値だけを選ばせ、JSON としての正しさとスキーマ適合の両方を保つ。これにより、生成されるすべてのトークンが構造的にも意味的にも正しくなり、出力 JSON は 100% 取り出せて、必ずエラーなくパースできる。

⚠ 注意モデルがプロンプトから自発的に正しい JSON を出すことに頼ってはいけない。関数定義をプロンプトに入れて構造化出力を期待するのは信頼性がなく、ここで身につけてほしいスキルでもない。
ℹ ヒント語彙 JSON ファイルを使って、トークンとその文字列表現をどう対応づけられるか考えてみよう。これは各生成ステップでどのトークンが有効かを判断するうえで非常に重要だ。

V.4 出力ファイル形式

プログラムは 1 つの JSON ファイル data/output/function_calling_results.json を出力する。プロンプトごとに JSON オブジェクトを 1 つ追加し、各オブジェクトはちょうど次のキーを持つこと：

  • prompt（文字列）：元の自然言語リクエスト
  • name（文字列）：呼び出す関数の名前
  • parameters（オブジェクト）：必要な引数すべてを正しい型で

V.4.1 出力例

[
    {
        "prompt": "What is the sum of 2 and 3?",
        "name": "fn_add_numbers",
        "parameters": {"a": 2.0, "b": 3.0}
    },
    {
        "prompt": "Reverse the string 'hello'",
        "name": "fn_reverse_string",
        "parameters": {"s": "hello"}
    }
]

V.4.2 検証ルール

  • ファイルは有効な JSON であること（末尾カンマなし、コメントなし）
  • キーと型は functions_definition.json のスキーマに完全一致すること
  • 出力のどこにも余計なキーや文章を含めないこと
  • 必須の引数はすべて含めること
  • 引数の型は関数定義（number、string、boolean など）と一致すること
⚠ 注意入力ファイルはピアレビュー中に変更される可能性がある。提供された例をもとに答えをハードコードしないこと。

V.5 性能と信頼性

実装は次を達成すること：

  • ほぼ完璧な精度：関数の選択と引数の抽出が 90% 以上正しい
  • 100% 有効な JSON：すべての出力がパース可能かつスキーマ準拠
  • 妥当な速度：一般的なハードウェアで全テストプロンプトを 5 分以内に処理
  • 堅牢なエラー処理：不正な入力、ファイルの欠如、エッジケースを適切に処理
ℹ 情報Qwen3-0.6B はわずか 5 億パラメータしかないが、適切な Constrained Decoding を使えば、はるかに大きなモデルに匹敵する信頼性を出せる。これは、モデルの大きさよりも構造による誘導の力を示している。

V.6 実装のテスト

  1. 入力ファイルが data/input/ にあることを確認する
  2. 実行：uv run python -m src [-functions_definition <function_definition_file>] [-input <input_file>] [-output <output_file>]
  3. output/function_calling_results.json が作られたか確認する
  4. JSON の構造と内容を検証する
  5. 関数名と引数の型が定義と一致するか確認する
⚠ 注意さまざまなエッジケースでテストすること：空文字列、大きな数値、特殊文字、間違った型、曖昧なプロンプト、複数の引数を持つ関数など。
CHAPTER VI

README の要件

Git リポジトリのルートに README.md を用意すること。目的は、プロジェクトを知らない人（仲間、スタッフ、採用担当者など）が、何のプロジェクトか・どう動かすか・どこで詳しい情報が得られるかをすぐ理解できるようにすることだ。

README.md には最低限、次を含めること：

  • 1 行目は斜体で次の文にすること：This project has been created as part of the 42 curriculum by <login1>[, <login2>[, <login3>[...]]].
  • 「Description」セクション：目的と簡単な概要を含め、プロジェクトを明確に紹介する。
  • 「Instructions」セクション：コンパイル・インストール・実行に関する情報。
  • 「Resources」セクション：テーマに関する定番の参考資料（ドキュメント、記事、チュートリアルなど）と、AI をどう使ったか（どの作業・どの部分に使ったか）の説明。
  • プロジェクトによっては追加セクションが必要（使用例、機能一覧、技術的な選択など）。

このプロジェクトでは、README.md に以下も含めること：

  • アルゴリズムの説明：Constrained Decoding のアプローチを詳しく説明する
  • 設計上の判断：実装における主要な選択を説明する
  • 性能分析：精度・速度・信頼性について論じる
  • 直面した課題：困難とその解決方法を記録する
  • テスト戦略：実装をどう検証したかを説明する
  • 使用例：プログラムの実行例を分かりやすく示す
ℹ 情報README は英語で書くこと。
CHAPTER VII

ボーナスパート

ボーナス機能（任意。合格には不要）：

  • Qwen/Qwen3-0.6B 以外の複数の LLM モデルへの対応
  • トークナイザの再実装：メインコードで encode と decode を直接使わず、get_logits_from_input_ids と get_path_to_vocab_file を使う
  • 高度なエラー回復の仕組み
  • パフォーマンス最適化（キャッシュ、バッチ処理）
  • 包括的なテストスイート
  • 生成過程の可視化
  • 入れ子になった複雑な関数引数への対応
  • トークナイザの encode（と任意で decode）メソッドの公開実装
  • エンコード・デコードが Constrained Decoding とどう統合されるかのデモ

ボーナス機能は README に書くだけでなく、実装されて動作する必要がある。評価中にデモを求められることもある。

CHAPTER VIII

提出とピアレビュー

いつも通り、課題は Git リポジトリに提出すること。ディフェンス（評価）ではリポジトリ内の作業だけがレビューされる。ファイル名が正しいか、ためらわず再確認しよう。

リポジトリには次を含めること：

  • src/ ディレクトリ（実装）
  • 依存関係管理のための pyproject.toml と uv.lock
  • llm_sdk/ ディレクトリ（提供パッケージからコピー）
  • data/input/ ディレクトリとテストファイル（デモ用）
  • 充実したドキュメントの README.md
  • その他、実行に必要なファイル
⚠ 注意output/ ディレクトリはリポジトリに含めないこと。ピアレビュー中に生成される。

評価中に、ときどきプロジェクトの小さな修正を求められることがある。ちょっとした挙動の変更、数行のコードの追加・書き直し、簡単に追加できる機能などだ。

このステップはすべてのプロジェクトに当てはまるわけではないが、評価ガイドラインに記載されている場合は備えておく必要がある。

このステップの目的は、プロジェクトの特定部分を本当に理解しているかを確かめることだ。修正は好きな開発環境（普段の環境など）で行ってよく、数分で終わる程度の内容である — 評価で特定の制限時間が定められていない限り。

例えば、関数やスクリプトの小さな更新、表示の変更、新しい情報を保存するためのデータ構造の調整などを求められるかもしれない。

詳細（範囲、対象など）は評価ガイドラインで指定され、同じプロジェクトでも評価ごとに異なる場合がある。
