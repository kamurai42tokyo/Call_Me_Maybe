🔰 1. ひとことで言うと

「人間の自由な言葉のお願いを、プログラムが確実に実行できる注文票（JSON）に変換するツール」です。ターミナルから動かすCLIプログラムとして作ります。

レストランを想像してください。お客さんは「えーと、パスタで、辛くないやつをひとつ」と、どんな言い方で注文してもかまいません。でも厨房に届く伝票は、必ず決まった書式で書かれています。この「自由な言葉 → 決まった書式の伝票」の変換を、AI（小型のLLM: Qwen3-0.6B）に書かせるのがこの課題です。

ただし、AIは放っておくと伝票の書式を平気で間違えます。そこで「今この瞬間に書いてよい文字」以外を物理的に選べなくするガードレール（constrained decoding）を自力で実装するのが核心です。「AIへのお願い（プロンプト）で頑張って正しく書いてもらう」のではなく、構造的に間違えられなくする——これがこの課題の要求です。また、どの関数を呼ぶべきかの判断もAI自身にさせます（文字列の一致で決めるなどの小細工は禁止されています）。

やらないこと: ボーナス課題（トークナイザの自作・生成過程の可視化・複数モデル対応など）は、必須部分が完了してから検討します。

🧩 4. どう作る？

役割ごとに部品（クラス／ファイル）を分けます。登場人物は6人です。

  • 受付係（__main__.py）— コマンドの引数を受け取る
  • 読み書き係（io_utils.py + models.py）— ファイルの読み込み・チェック・書き出し。チェックにはpydantic を使う
  • 選択係（selector.py）— どの関数を呼ぶかAIに選ばせる
  • 生成係（decoder.py）— 制限つきでJSONを1トークンずつ作る
  • 辞書係（vocab.py）— AIの語彙（トークンと文字の対応表）を管理する
  • 進行係（pipeline.py）— 全体の流れと時間を管理する

作り方の中心になるアイデアは4つです。

アイデア1: 選択肢を絞って選ばせる
AIは、次に出すトークンの全候補それぞれに点数（logits）を付けます。ルールに合わない候補の点数を最低にしてしまえば、その候補は絶対に選ばれません。あとは残りからいちばん点数の高いものを選ぶだけ（greedy）。関数選びなら、点数を残すのは「実在する関数名」だけ。だから答えは必ず有効になります。
アイデア2: JSONの道案内役（状態機械）
「今は数字を書く場面」「今は文字列の途中」のように現在の場面を管理する状態機械を作り、場面ごとに「書いてよい文字」を決めます。JSONの文法と、選んだ関数の型（スキーマ）の両方をこの場面に織り込むので、文法違反も型違反も起こせません。
アイデア3: 決まりきった部分はAIに書かせない
キー名や記号（{ } : , "）は最初から決まっているので、AIに書かせず自動で埋めます。AIに生成させるのは「値」の部分だけ。速くて確実です。
アイデア4: 速さの工夫
場面ごとの「許可トークン一覧」は起動時に一度だけ計算しておき、生成中は表引きだけで済ませます（5分制限への対策）。また、トークンが文字の途中で切れてしまう問題は、文字単位の前方一致で照合することで解決します。
ちなみに: pytorch・transformers・outlines などの既製の便利ライブラリは使用禁止です。使えるのは numpy / json / pydantic と提供SDKだけ。だからこそ、この仕組みを自力で作ることに意味があります。

✅ 5. どう確かめる？

  • 文法の道案内役を最初に固める — 状態機械はAI抜きで単体テストできるので、いちばん先にテストを書いて固めます
  • 全出力を機械チェック — 出力ファイルを読み直して「100%壊れていないJSONか・型どおりか」をプログラムで確認します
  • 意地悪テストをする — 変な値（空文字・大きな数・小数・特殊文字）や曖昧なお願い文を食べさせて、それでも壊れないか確認します
  • 壊れた入力ファイルを試す — ファイル欠落・不正JSONを渡して、わかりやすいエラーメッセージが出るか確認します
  • 時間を計る — 全体の処理時間を計測して、5分以内に収まることを確認します

🛠 6. 作る順番

  1. まず一番小さい形で通す — 関数1つ・引数1個（数値だけ）のお願いが、最初から最後まで動く状態を作る
  2. 全部の型と関数選びに対応 — 文字列・真偽値などすべての型、AIによる関数選択、エラー処理をそろえ、精度と時間の目標をクリアする
  3. 余裕があれば挑戦 — トークナイザの自作や、生成過程の可視化に取り組む

⚠️ 7. つまずきやすいポイント

  • 小さいAIなので賢さに限界がある — 0.6Bという小型モデルは判断を間違えやすい。関数の説明の見せ方（プロンプト）を工夫して精度を稼ぎます。正しさそのものはガードレールが保証してくれるので、プロンプトはあくまで「精度向上の補助」という位置づけです
  • 処理が5分を超える — 許可リストの事前計算、決まりきった部分の一括埋め、プロンプトの短縮で対策します
  • トークンの途中切れの扱いでバグ — いちばんバグが出やすい部分。AI抜きの単体テストを先に整備して、文法部分を固めてから組み込みます

📖 8. 用語集

LLM
大規模言語モデル。大量の文章から「次に来る言葉」を予測することを学んだAI。この課題では小型の Qwen3-0.6B を使う。
トークン
AIが文章を読み書きするときの最小単位。単語より細かく区切られることが多く、1つの文字の途中で切れることさえある。
logits
AIが「次のトークン候補」の一つひとつに付ける点数。点数が高い候補ほど選ばれやすい。
constrained decoding（制限つき生成）
ルールに合わないトークンを選べないようにしながらAIに文章を作らせる方法。お願いではなく仕組みで、出力が必ずルールどおりになる。
プロンプト
AIに渡す指示やお願いの文章。この設計では正しさの保証には使わず、精度向上の補助と位置づける。
JSON
波かっこ { } や引用符で書く、プログラム同士のデータ受け渡しの定番書式。書き方のルールが厳密に決まっている。
スキーマ
データの設計図。「このキーは数値」「このキーは文字列」のように、含むべき項目と型を決めたもの。
pydantic
データがスキーマ（型）どおりかを自動でチェックしてくれる Python のライブラリ。この課題で数少ない使用OKのライブラリの一つ。
状態機械
「今どの場面にいるか」を覚えておき、場面ごとに「次にしてよいこと」を決める仕組み。信号機のように場面が順々に切り替わっていく。
greedy（貪欲法）
毎回いちばん点数の高い候補を選ぶ決め方。結果が毎回同じになり、デバッグしやすい。
語彙（vocab）
AIが知っている全トークンの一覧表。トークンの番号と文字の対応表になっている。
CLI
ターミナルに文字でコマンドを打って動かすプログラムの形。マウスで操作する画面は持たない。
